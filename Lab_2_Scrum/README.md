## 1. Scrum: Переход от Scrumfall к честному Scrum

**Проблема «Scrumfall»:** команда тратит 3 недели на «большое проектирование» (Big Upfront Design), после чего пытается написать весь код за один длинный спринт. В итоге - поздняя обратная связь, высокие риски и релиз.

**Решение:** 2-недельные спринты, короткие этапы исследования (Spike), инкрементальная поставка.

### Роли в команде
*   **Product Owner (PO):** Отвечает за Product Backlog, собирает требования к персонализации.
*   **Scrum Master (SM):** Следит за процессом, помогает убрать блокеры, фасилитирует митинги.
*   **Команда разработки:** Backend, Frontend, QA, Data Scientist.

### Артефакты
*   **Product Backlog:** Парсер новостей, База данных статей, Лента пользователя, ML-модуль персонализации, Личный кабинет.
*   **Sprint Goal (1-й спринт):** «Запустить MVP: парсинг 3 источников, вывод общей ленты и базовая регистрация».

### События спринта (2 недели)
*   **Sprint Planning (2 часа):** Берем задачи из топа бэклога, оцениваем в Story Points.
*   **Daily Scrum (15 мин):** Синхронизация. Что сделал, что буду делать, какие препятствия.
*   **Sprint Review (1 час):** Демонстрация инкремента PO и стейкхолдерам. Получение фидбека.
*   **Sprint Retrospective (1 час):** Обсуждение процессов внутри команды, поиск улучшений.

## 2. Kanban: Управление потоком задач

Мы используем Kanban для визуализации потока и ограничения незавершенной работы (WIP). 
Подробная схема доски находится в файле `board.md`.

**Правила потока:**
1.  **Backlog** → задачи ждут своей очереди.
2.  **To Do** → задачи в текущем спринте.
3.  **In Progress (WIP: 3)** → в работе не более 3 задач.
4.  **Code Review (WIP: 2)** → проверка кода коллегой.
5.  **Testing (WIP: 2)** → проверка QA.
6.  **Done** → задача готова к демо.

**Блокеры:** Если задача ждёт ответа от API, она помечается красным флажком `BLOCKED` и не тратит WIP-лимит.

## 3. Практики XP (Extreme Programming)

### 3.1. Small Releases (Частые релизы)
*   **Как делаем:** Каждые 2 недели выкатываем рабочую версию на прод-сервер.
*   **Зачем:** Пользователи сразу видят работающую ленту. Если алгоритм плох, узнаем через 2 недели.
*   **Риск без практики:** Потратим месяцы на ML-модель, которая не понравится пользователям.

### 3.2. Continuous Integration (Непрерывная интеграция)
*   **Как делаем:** Каждый пушит код в общую ветку не реже 2 раз в день. При пуше запускаются автотесты.
*   **Зачем:** Парсер, лента и профиль пишутся разными людьми. 
*   **Риск без практики:** Ветки разойдутся, потратим дни на конфликты в коде.

### 3.3. Refactoring (Рефакторинг)
*   **Как делаем:** Улучшаем структуру кода без изменения поведения (например, переписываем метод формирования ленты, чтобы добавить туда рекомендации).
*   **Зачем:** Агрегатор растет. Если не чистить код, скорость добавления фич упадет.
*   **Риск без практики:** Наступит «технический долг», проект станет Legacy-монолитом.

|--------|------------------|--------------------------------|
| **Аналитика** | 3 недели пишем ТЗ | Небольшие User Stories с критериями (DoR) |
| **Планирование** | Один огромный релиз в конце | Релизы каждые 2 недели (Small Releases) |
| **Работа** | Пишем код от начала до конца | Ограничение WIP, поток задач (Kanban) |
| **Обратная связь** | После финального релиза | Демо в конце каждого спринта |
| **Риски** | Высокие (не успеть / сделать не то) | Низкие (гибкая реакция на изменения) |
